The docs' "Authorizing Resources" section: "All resources can be accessed via an access token … `fetch('https://dummyjson.com/auth/RESOURCE', … 'Authorization': 'Bearer …'`". Observed live: `/auth/products` (GET), `/auth/products/add` (POST), `/auth/products/1` (PUT, DELETE) all return `401` without a token and succeed with one.

**Schema facts observed live (for `pytest-api` schema resolution):**
- Product: 22 distinct fields; 21 appear on all 194 products, `brand` on only 102 → `brand` is optional.
- The list item and the detail record of the same product are identical.
- PUT/PATCH responses have 11 fields (not 22). DELETE responses have 24 (22 + `isDeleted`, `deletedOn`).
- Every error body observed is exactly `{"message": "<string>"}`.
- `meta.updatedAt` values are stable between calls (range observed: `2024-11-08…` to `2026-08-31…`).

Rules marked **(observed live)** are not stated in the docs — they are what the API actually did when called on 2026-09-27; rules marked **(inferred)** are expected-behavior assumptions with no source statement, recorded so test design can mark them `[Assumption]`._

- **Feature summary:** DummyJSON is a free fake REST API of placeholder JSON data for front-end and test projects. The auth module issues JWT access and refresh tokens for any published user (`dummyjson.com/users`); the products resource is a 194-item e-commerce catalog with pagination, field selection, sorting, date filtering, search and categories. Writes are simulated.
- **In scope:** the 3 auth endpoints; the 10 product endpoints; the `/auth/` Bearer mirror of products.
- **Out of scope:** carts, recipes, users (including the `/users/login` alias), posts, comments, todos, quotes, tools, dynamic image, mock HTTP, `/test`, `/ip`.
- **Business rules / edge cases:**
  - `RULE-auth-login-returns-token-pair`: login returns the user's `id, username, email, firstName, lastName, gender, image` plus `accessToken` and `refreshToken` (docs). Both are JWTs whose claims carry the same identity fields plus `iat`/`exp` (observed live). — affects `POST /auth/login`
  - `RULE-auth-login-sets-token-cookies`: "Tokens are returned in the response and set as cookies" (docs). — affects `POST /auth/login`
  - `RULE-auth-expiry-configurable`: `expiresInMins` is optional and defaults to 60 (docs). Observed live: `exp - iat` equals `minutes × 60`; the default gives 3600 s; `0` gives 30 days (2592000 s); `43201` and `-1` both return `500 "Maximum access token expire time can be 43200 minutes"`. — affects `POST /auth/login`, `POST /auth/refresh`
  - `RULE-auth-bad-credentials-generic-error` (observed live): wrong password and unknown username both return `400 "Invalid credentials"`. — affects `POST /auth/login`
  - `RULE-auth-login-requires-credentials` (observed live): a missing `username` and/or `password` returns `400 "Username and password required"`. — affects `POST /auth/login`
  - `RULE-auth-bearer-required-on-auth-routes`: `/auth/me` and `/auth/RESOURCE` take the access token as `Authorization: Bearer <token>` (docs). Observed live: no token returns `401 "Access Token is required"`. — affects `GET /auth/me`, `/auth/products…`
  - `RULE-auth-cookie-token-accepted`: the access token can be sent as a cookie (docs: "Include cookies (e.g., accessToken)"). Observed live: `Cookie: accessToken=<token>` works on `/auth/me`. — affects `GET /auth/me`
  - `RULE-auth-invalid-token-rejected` (inferred): a malformed token, a forged signature, a wrong scheme, or a token without the `Bearer ` scheme should be rejected with `401`. Observed live: malformed → `500 "invalid token"`; forged signature → `500 "invalid signature"`; `Basic <token>` → `500`; raw token without a scheme → `200` (accepted). — affects `GET /auth/me`
  - `RULE-auth-expired-token-rejected` (observed live): once a token's `exp` has passed it returns `401 "Token Expired!"`. Obtainable for real with `expiresInMins: 1`. — affects `GET /auth/me`
  - `RULE-auth-refresh-issues-new-pair`: refresh returns a new `accessToken` and `refreshToken` "without username and password"; the refresh token may come from the body or the cookie (docs). — affects `POST /auth/refresh`
  - `RULE-auth-refresh-token-required` (observed live): an invalid refresh token returns `403 "Invalid refresh token"`; none at all returns `401 "Refresh token required"`. — affects `POST /auth/refresh`
  - `RULE-auth-refresh-token-single-use` (inferred): a refresh token should stop working once it has been exchanged (rotation), so a leaked one can't be replayed. Observed live: an already-used refresh token is accepted again (`200`, new pair), and refresh tokens always last 30 days. — affects `POST /auth/refresh`
  - `RULE-auth-token-types-not-interchangeable` (inferred): an access token and a refresh token have different jobs. Observed live: each is accepted in the other's place (`/auth/me` with the refresh token → `200`; `/auth/refresh` with the access token → `200`). — affects `GET /auth/me`, `POST /auth/refresh`
  - `RULE-auth-me-hides-sensitive-fields` (inferred): an identity endpoint shouldn't expose secrets. Observed live: `/auth/me` returns `password`, `ssn`, `ein`, `bank`, `crypto`. — affects `GET /auth/me`
  - `RULE-products-default-page-30`: "By default you will get 30 items" (docs). Observed live: `skip 0`, `limit 30`, `total 194`. — affects `GET /products`
  - `RULE-products-limit-skip-paginate`: `limit` and `skip` paginate; `limit=0` gets all items (docs). Observed live: `limit=5&skip=10` → ids 11–15; `skip` past the end → `products: []`, `total` unchanged. — affects `GET /products`, `/products/search`, `/products/category/{slug}`
  - `RULE-products-invalid-paging-rejected` (observed live): negative or non-numeric `limit` → `400 "Invalid 'limit' - should be a positive number"`; `skip=-1` → `400 "Invalid 'skip' - should be a positive number"`. — affects `GET /products`
  - `RULE-products-select-fields`: `select` with comma-separated values, or repeated `select` params, returns only those keys (docs). Observed live: `id` is always included too. — affects `GET /products`
  - `RULE-products-sort-by-order`: `sortBy` is a field name; `order` is `asc` or `desc` (docs). Observed live: an invalid `order` → `400 "Invalid 'order' - should be either 'asc' or 'desc'"`; an unknown `sortBy` field is silently ignored (`200`, default id order). — affects `GET /products`
  - `RULE-products-modified-date-filter`: `modifiedAfter` / `modifiedBefore` (ISO 8601) keep only products whose `meta.updatedAt` is in range; they work on all list endpoints and combine with the other params (docs). Observed live: an invalid date → `400 "Invalid 'modifiedAfter' - should be a valid ISO 8601 date, e.g. 2025-01-01T00:00:00Z"`. — affects `GET /products`, `/products/search`, `/products/category/{slug}`
  - `RULE-products-delay-max-5000`: `delay` simulates latency, "any number between 0 and 5000 milliseconds" (docs intro, all resources). Observed live: `6000` → `400 "Delay should be less than 5 seconds (5000 milliseconds)"`. — affects `GET /products` (inferred — the docs state it for all resources)
  - `RULE-products-unknown-id-not-found` (observed live): an unknown or non-numeric id returns `404 "Product with id '<id>' not found"`, on GET, PUT, PATCH and DELETE. — affects `/products/{id}`
  - `RULE-products-search-title-description` (observed live): `q` matches title/description ignoring case (`phone` and `PHONE` both return 23); no match → `products: []`, `total 0`; empty `q` returns all 194. — affects `GET /products/search`
  - `RULE-products-categories-lists-agree` (observed live): `/products/categories` (24 `{slug, name, url}` objects) and `/products/category-list` list the same slugs in the same order. — affects both category routes
  - `RULE-products-category-filter` (observed live): a category filter returns only that category (`smartphones`: 16); an unknown category returns `200` with an empty list, not `404`. — affects `GET /products/category/{slug}`
  - `RULE-products-writes-simulated`: add "will not add it into the server", update "will not update it", delete "will not delete it" — each simulates the call and returns the result (docs). Observed live: reading an added id → `404`; a patched product reads back unchanged; delete returns `isDeleted: true` and an ISO `deletedOn`. — affects `POST /products/add`, `PUT`/`PATCH`/`DELETE /products/{id}`
  - `RULE-products-add-validates-body` (inferred): a new product should need a body with valid types. Observed live: `{}` → `201 {"id": 195}`; `price: "free"` → `201`, echoed. — affects `POST /products/add`
  - `RULE-products-update-response-shape` (inferred): the docs say update returns the "updated product with modified data", which implies the same shape as a read. Observed live: PUT/PATCH return 11 of the product's 22 fields. — affects `PUT`/`PATCH /products/{id}`

## Open questions / follow-ups
- **No spec exists**, so there is no machine-readable schema. Response schemas must be built from the docs examples plus the live field census above; the docs examples elide fields (`...`), so they alone aren't enough.
- **The docs describe no error cases at all.** Every status code and message above marked (observed live) came from live calls on 2026-09-27 and could change without notice.
- **`expiresInMins: 0` gives a 30-day token** and `-1` gives a `500` with a misleading "Maximum…" message. Neither is documented; test design should decide whether `0` is a boundary case worth pinning.
- **One transient dropped connection** was seen on `GET /products?sortBy=nosuchfield`; it didn't reproduce in two retries (`200` both times). Noted in case it recurs; not treated as a rule.
- The `delay` param is documented for all resources; whether it belongs in this project's scope is a test-design call.
